**庁内で、定型の作業を自動化した経験**をお持ちの方がいらっしゃいます。

**その経験を、どう書けばよいか**というご相談です。

この記事では、**評価される点**と、**書き方**を扱います。

## 自動化しても、責任の所在は変わりません

**地方自治法第138条の2の2**です。

> **普通地方公共団体の執行機関は、当該普通地方公共団体の条例、予算その他の議会の議決に基づく事務及び法令、規則その他の規程に基づく当該普通地方公共団体の事務を、自らの判断と責任において、誠実に管理し及び執行する義務を負う。**

**「自らの判断と責任において」**と書かれています。

**事務を機械に処理させても、この義務が移るわけではありません。**

**したがって、自動化の設計では、次の3点が必要になります。**

| 必要なこと | 内容 |
|---|---|
| ① 確認の工程 | **誰が、どの時点で確かめるか** |
| ② 例外の処理 | 想定外の入力をどう扱うか |
| ③ 記録 | 何を、どこまで残すか |

**この3点を設計した経験こそが、書くべき内容**です。

**「自動化した」だけでは、評価が定まりません。**

## 何が評価されるか

| 要素 | 内容 |
|---|---|
| ① 対象の選び方 | **なぜその作業を選んだか** |
| ② 工程の分解 | どこを機械に、どこを人に残したか |
| ③ 確認の設計 | 誤りをどう検出するか |
| ④ 例外の扱い | 止まったときの手順 |
| ⑤ 引継ぎ | 他の職員が運用できるか |
| ⑥ 結果 | 件数、時間の変化 |

**①が起点**です。

**件数が多く、手順が決まっていて、判断を伴わない作業。**

**この条件を満たす作業を選べたかどうか**が、設計の力として読まれます。

**⑤について。**

**作った本人しか直せない状態は、組織では評価されにくい**ものです。

**手順書を残した、他の職員に運用を引き継いだ**という事実があれば書いてください。

## 書き方の例

**悪い例**

> 庁内でRPAを導入し、業務を効率化しました。

**良い例**

> ◯◯に関する定型の作業について、**年間約◯件・月◯時間を要していた工程を対象に自動化を設計。**入力の様式を統一したうえで、**機械に処理させる範囲と、職員が確認する範囲を分離。****想定外の入力で停止した場合の手順書を作成し、係◯名に運用を引き継ぎ。**運用の開始から◯か月で、対象の工程の処理の時間が約◯割減少。

**「対象の選定」「分離」「例外の手順」「引継ぎ」「結果」**が入っています。

**基本の型は**[公務員の職務経歴書｜民間で読まれる形にする基本](senko-shokumu-kihon.html)**に整理しています。**

## どの転職先で効くか

| 領域 | 使いどころ |
|---|---|
| ① 自治体向けのシステム | **現場の工程が分かる** |
| ② 業務の改善の支援 | 工程の分析、標準化 |
| ③ 業務の受託 | 受託した業務の効率化 |
| ④ 社内の情報システム | 内製の支援、運用の設計 |
| ⑤ 事務の集約の部門 | 手順の設計、品質の管理 |

**③について。**

**窓口や事務を受託する会社では、受託した業務をどう効率化するかが収益に直結**します。

**行政の事務の工程を知っている人**は、そこで必要とされます。

**探し方は**[公務員経験が活きる求人の探し方](senko-sagasu-kyujin.html)**に整理しています。**

:::insight
自動化の経験について、**面談でお伝えしているのが「止まったときの設計を書いてください」**という点です。書類を拝見すると、**「◯時間削減」という結果だけが書かれている**ことがあります。ところが、**業務の自動化で実際に問われるのは、うまくいかなかったときの扱い**です。想定外の入力が来た、様式が変わった、件数が急に増えた。**そのときに、誰が気づき、どう戻すか。**行政の事務では、**処理を誤ると、住民や事業者に直接影響します。**ですから、**止める条件、戻す手順、確認の担当**を決めておく必要があります。**この設計をした経験は、民間でもそのまま評価されます。**理由は、**同じ問題が起きるから**です。書類には、**「想定外の入力で停止した場合の手順書を作成」「処理の結果を職員が確認する工程を残した」**と書いてください。**削減の数字より、この一文が効くことがあります。**ご利用は無料です（紹介手数料は採用企業の負担です）。
:::

## 始める前に考えること

| 確認すること | 内容 |
|---|---|
| ① すでに回した経験があるか | **実績の整理が先** |
| ② 所属の規程・体制 | 情報の担当への確認 |
| ③ 対象の作業 | 件数、手順、判断の有無 |
| ④ 応募したい求人の条件 | ツールの指定があるか |
| ⑤ 期限 | 応募の時期までに間に合うか |

**①を最初に置いてください。**

**庁内で何かを自動化した経験があるなら、その整理が先**です。

**②について。**

**⚠ 庁内のシステムやデータの取扱いには規程があります。****必ず、所属の情報の担当に確認してから進めてください。**

**なお、ツールを習得すれば転職できる、という関係にはありません。**

**どの作業を選び、どう設計したか**が、評価の対象です。

## 実績がない場合

| やること | 内容 |
|---|---|
| 対象を探す | **自分の担当の定型の作業** |
| 手順を書き出す | 工程を分解する |
| 小さく試す | 規程の範囲で |
| 結果を記録する | 件数、時間の変化 |

**2行目だけでも、材料になります。**

**工程を分解して書き出す作業**は、**自動化しなくても価値があります。**

**面接では、「◯◯の作業を◯工程に分解し、うち◯工程は判断を伴わないと整理した」**と話せます。

[経験の言い換えから相談する](../apply.html)こともできます。

## 面接で聞かれやすいこと

| 質問の趣旨 | 用意しておくこと |
|---|---|
| なぜその作業を選んだか | **選定の基準** |
| どこを人に残したか | 判断が必要な工程 |
| 止まったときの扱い | 手順、担当 |
| 引継ぎ | 手順書、説明した人数 |
| 結果 | 件数、時間の変化 |

**2行目です。**

**すべてを機械に任せなかった理由**を説明できると、設計の考え方が伝わります。

## 対象の選び方

**自動化に向く作業と、向かない作業があります。**

| 条件 | 向く | 向かない |
|---|---|---|
| 件数 | 多い | 年に数件 |
| 手順 | 決まっている | 毎回変わる |
| 判断 | 伴わない | **要件の解釈が必要** |
| 様式 | 統一されている | 提出者ごとに異なる |
| 期限 | 平準化している | 特定の時期に集中 |

**3行目が最も重要**です。

**要件の解釈を伴う作業は、自動化の対象にしないでください。**

**判断を機械に委ねると、責任の所在が曖昧になります。**

**5行目について。**

**繁忙期に集中する作業は、効果が大きい一方、停止したときの影響も大きくなります。**

**この見極めを説明できると、設計の考え方が伝わります。**

## よくある失敗

**1. 削減の数字だけを書く**

**止まったときの設計**を書いてください。

**2. 対象の選び方を書かない**

**選定の基準**が設計の力です。

**3. 人に残した工程に触れない**

**責任の所在**が伝わりません。

**4. 引継ぎを書かない**

**属人的に終わっていない**ことが評価されます。

**5. 規程を確認せずに試す**

**情報の担当に確認**してください。

**6. ツールの名前だけを書く**

**工程の分解**が中身です。

**7. 実績より先に学習を始める**

**既にある実績の整理が先**です。

**8. 習得すれば転職できると考える**

**どう設計したか**が評価の対象です。

:::insight
ここまで設計の話をしておいて逆のことを言いますが、**自動化が実現しなかった経験にも、書ける部分があります。**面談で拝見していると、**「検討したが、導入に至らなかったので書けない」と考える方**がいらっしゃいます。ところが、**なぜ見送ったかを説明できるなら、それは判断の経験**です。件数が想定より少なかった、様式が毎年変わる、判断を伴う工程が多かった、費用に見合わなかった。**いずれも、対象を評価した結果**です。そして、**民間でも、導入の可否を判断する場面**があります。**「やってみたが合わなかった」を説明できる人**は、**同じ失敗を繰り返しません。**書類には、**「◯◯の工程を対象に検討したが、判断を伴う分岐が多く、標準化が先と判断。手順書の整備を優先した」**と書いてください。**見送った判断も、成果として書けます。**在職中でも、情報収集だけでも構いません。
:::

## まとめ

- **地方自治法第138条の2の2**は、**執行機関が事務を自らの判断と責任において誠実に管理し及び執行する義務**を負うとしています
- **自動化しても、この義務が移るわけではありません。**だから、**確認の工程・例外の処理・記録**の設計が必要になります
- 評価されるのは、**対象の選び方、工程の分解、確認の設計、例外の扱い、引継ぎ、結果**です
- **止まったときの設計**を書いてください。削減の数字より効くことがあります
- **人に残した工程**に触れてください。責任の所在が伝わります
- **規程を確認してから**試してください
- **見送った判断も、成果として書けます**

行政が相手の求人もまとまっています。[行政が相手の求人を見てみる](../?gov=1)。

## よくある質問

### 自分で作らず、事業者に委託した場合はどう書きますか

**発注した側の経験として書いてください。**「◯◯の作業を対象に、仕様を作成し、事業者◯者から提案を受けて選定。要件の整理と、受入れの確認を担当」という形です。**仕様を書ける人**は、民間でも必要とされます。とくに、**自治体向けのシステムの会社**では、**発注する側の考え方を知っている人**が求められます。扱いは[技術職の転職｜事務職と何が違うか](senko-tachiba-gijutsu.html)に整理した考え方と同じです。**「作っていないから書けない」ではありません。****何を決めたか**を書いてください。

### 効果が小さく、書くほどではない気がします

**規模より、設計を書いてください。**月に数時間の削減でも、**対象の選び方、工程の分解、確認の設計**は同じです。そして、**中途採用で見られているのは、考え方**です。「大規模な導入の経験」を求める求人は限られます。一方、**「業務を分解して改善できる人」を求める求人は多い**です。書き方は、**「◯◯の作業について、◯工程に分解し、うち◯工程を自動化。残りは判断を伴うため職員が実施」**という形です。**判断の跡が見える書き方**にしてください。

### ツールの名前は、書いたほうがよいですか

**併記してください。**ただし、**名前だけでは中身が伝わりません。**「◯◯を用いて」と手段として書き、**中身は工程と結果で書く**のが基本です。なお、**求人票でツールが指定されている場合、その経験が要件になっている**ことがあります。「必須」か「歓迎」かで扱いが違うため、**応募条件の欄を確認**してください。読み方は[求人票の読み方｜どこを見れば実態が分かるか](senko-sagasu-kyujinhyo.html)に整理しています。**別のツールでの経験でも、考え方が共通していれば説明できます。**

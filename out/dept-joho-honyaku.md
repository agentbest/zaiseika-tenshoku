情報政策課やDX推進の担当から転職しようとすると、たいてい最初にこう思います。

**「自分は開発をしていないので、技術職としては応募できない」**

半分は当たっていて、半分は外れています。たしかに、コードを書く求人には届きにくい。ただし**開発しない情報系の職種は、民間にいくつもあります。**むしろ、そちらのほうが求人の数が多い領域もあります。

この記事では、情報政策課・DX推進の仕事を分解して、それぞれが求人票でどう書かれているかを並べます。訳語が分かれば、検索する言葉も応募先の選び方も変わります。

## この部署の中心にあるのは「つなぐこと」です

先に、この部署の立ち位置を押さえます。

行政手続における特定の個人を識別するための番号の利用等に関する法律（番号法）第1条は、この法律の目的をこう書いています。

行政機関、地方公共団体その他の行政事務を処理する者が、個人番号及び法人番号の有する**特定の個人及び法人その他の団体を識別する機能**を活用し、並びに当該機能によって**異なる分野に属する情報を照合してこれらが同一の者に係るものであるかどうかを確認することができるものとして整備された情報システムを運用**して、**効率的な情報の管理及び利用**並びに他の行政事務を処理する者との間における**迅速な情報の授受**を行うことができるようにする――。

長い条文ですが、中心は1つです。

**異なる分野にある情報が、同じ人のものかどうかを確認できるようにする。**

税、福祉、保険、年金。庁内では別々のシステムに、別々の形式で入っています。**それを照合できる状態にするのが、この仕事の中心です。**

システムを作ることではありません。**つなぐことです。**

そして、つなぐには全部の分野の業務を知らなければなりません。情報政策課が庁内のほぼ全部署と関わるのは、ここから来ています。

## 情報政策課・DX推進が実際にやっていること

自治体によって所管の範囲は違いますが、おおむね次の仕事が入ります。

- 基幹システムの調達（仕様書の作成、事業者の選定、契約、検収）
- システムの更改、データ移行の計画と検証
- 標準化への対応（国が定める仕様への適合、移行の工程管理）
- 庁内の情報連携、システム間のデータの受け渡し
- 各課からの要望の受付と、改修の優先順位づけ
- ネットワークと端末の管理、運用保守事業者との調整
- 情報セキュリティポリシーの策定と運用、研修
- 個人情報の取扱いに関する審査、目的外利用の可否の判断
- オンライン申請の導入、窓口業務の見直し
- 統計・データの庁内提供、公開データの整備
- 事業者との折衝、障害発生時の対応

**開発はしていません。**やっているのは、**要件を決めること、選ぶこと、動かすこと、止まったときに直させること**です。

これは民間でいう**情報システム部門**そのものです。開発は外部に出し、社内では企画と管理を持つ。多くの企業がこの形をとっています。

## 庁内の言葉と、求人票の言葉の対応

| 庁内での言い方 | 求人票での言い方 |
|---|---|
| システムの調達、仕様書の作成 | 要件定義、RFP作成、ベンダー選定 |
| 事業者の選定、契約、検収 | 調達、ベンダーマネジメント、受入検証 |
| システムの更改、データ移行 | システム移行、リプレース、データ移行 |
| 標準化への対応 | 標準仕様への適合、システム統合 |
| 庁内の情報連携 | データ連携、システム間連携 |
| 各課からの要望の受付と優先順位づけ | 要件管理、業務要件のとりまとめ |
| 改修の工程管理 | プロジェクト管理、進行管理 |
| ネットワークと端末の管理 | 情報システム運用、インフラ運用 |
| 運用保守事業者との調整 | ベンダーマネジメント、運用管理 |
| 情報セキュリティポリシー | 情報セキュリティ管理、規程整備 |
| 個人情報の取扱いの審査 | 個人情報保護、データガバナンス |
| オンライン申請の導入 | 業務のデジタル化、業務改革 |
| 窓口業務の見直し | 業務プロセス改革、オペレーション改善 |
| 障害発生時の対応 | 障害対応、インシデント管理 |

並べると、**情報システム部門、業務改革、データガバナンスの3つの領域にまたがっている**ことが分かります。

:::insight
この部署の方の書類で、いちばんもったいないのが**「開発経験がない」を理由に応募先を狭めてしまうこと**です。求人票の「要件定義」「ベンダーマネジメント」「RFP作成」は、**まさに情報政策課がやっている仕事の名前**です。とくに**基幹システムの調達を通した経験は、民間でも持っている人が限られます。**仕様書を書き、事業者を選び、移行を検証し、動かなかったときに直させる。この一連を数億円規模で回した経験は、外から採用しようとしても簡単には見つかりません。検索する語を「システムエンジニア」から「情報システム」「社内SE」「要件定義」「ベンダーマネジメント」に変えるだけで、出てくる求人の層が変わります。
:::

## 民間の情報システム部門と、どこが同じでどこが違うか

訳語の対応だけでは伝わりにくいので、**同じところと違うところ**を並べておきます。面接でそのまま使えます。

**同じところ**

- 開発は外部に出し、社内では要件と管理を持つ
- 利用部門から要望が上がり、優先順位をつけて改修する
- 事業者を選び、契約し、検収し、運用させる
- 稼働後に止まったら、原因を切り分けて直させる
- セキュリティの規程を作り、守らせる

**違うところ**

- **調達の手続が法令と規則で決まっている**（随意契約にできる範囲が限られる）
- **仕様を決めた時点で、当面の変更が難しい**（契約と予算の枠があるため）
- **利用部門を選べない**（全部署が対象で、断るという選択がない）
- **個人情報の取扱いに、条例と審査の手続が入る**
- **予算が単年度で区切られる**（複数年にまたがる契約は債務負担行為が要る）

この5つのうち、面接でいちばん効くのは**1つ目と2つ目**です。民間の情報システム部門でも調達の手続はありますが、**法令で縛られている環境で仕様を固めきる経験**をしている人は多くありません。

**「あとから直せない前提で、最初に要件を詰め切る進め方をしてきた」**という説明は、基幹システムの入替えを控えている企業には強く響きます。

## この経験がとくに高く評価される場所

### 1. 事業会社の情報システム部門

いちばん自然な接続先です。開発は外部に出し、社内では企画と管理を持つ。**構造がそのまま重なります。**

効くのは3点です。**要件をまとめる力**（各課からの要望を優先順位づけしてきた経験）、**事業者を選ぶ力**（仕様書と選定の経験）、**止まったときに動かす力**（障害対応と事業者への指示）。

とくに、**基幹システムの更改を通した経験**は直接使えます。企業でも基幹システムの入替えは10年に一度の規模の事業で、経験者が足りていません。

### 2. 自治体を顧客にするシステム会社

自治体向けの基幹システム、クラウドサービス、業務支援の会社です。

ここでは、**発注者側にいた経験そのものが値になります。**どういう仕様書が書かれ、何が検収の基準になり、どこで現場が止まるのか。**外からは見えません。**導入で失敗する案件の多くは、この理解の欠落から来ます。

職種としては、導入支援、カスタマーサクセス、提案企画、プリセールスといった名前になります。

[行政が相手の求人を見てみる](../?gov=1)

### 3. 業務改革・オペレーション改善

オンライン申請の導入や窓口業務の見直しを担当していた方の接続先です。

企業側では、業務プロセス改革、オペレーション改善、業務設計といった職種になります。**紙の手続をどう置き換えるかを、現場の抵抗を含めて経験している人**は多くありません。

ここで効くのは、**「置き換えられなかったもの」を説明できること**です。オンライン化を進めると、必ず残る手続が出てきます。本人確認が要るもの、添付書類が原本でなければならないもの、対面でなければ聞き取れないもの。**なぜ残したのかを説明できると、机上の改善しか知らない人と差が付きます。**

### 4. 情報セキュリティ・データ保護

セキュリティポリシーの策定と運用、個人情報の取扱いの審査を担当していた方の接続先です。

企業側では、情報セキュリティ管理、データガバナンス、内部統制といった職種になります。

自治体は、**個人情報の取扱いについて条例と審査の手続を持っています。**目的外利用の可否を、規程に照らして判断する。この経験は、企業のデータ利活用の場面でそのまま使えます。**「使ってよいか」を判断できる人は、技術が分かる人より少ない**からです。

ただし、この方向は**求人の数が限られ、資格や実務年数が要件になることもあります。**方向1と並行して見ておくのが現実的です。

## 職務経歴書でつまずきやすい点

**1. 「開発経験なし」と書いてしまう**

無いものを申告する必要はありません。**あるもの（要件定義、調達、移行、運用管理）を書いてください。**

**2. 使った製品名を並べる**

読み手が知らない自治体向け製品の名前を並べても伝わりません。**「基幹系システムの更改」「住民記録系のデータ移行」のように、機能で書いてください。**

**3. 規模を書かない**

**契約金額、対象の業務数、移行したデータの件数、関わった課の数、端末の台数。**規模が伝わる数字を必ず入れてください。情報政策課は扱う規模が大きい部署です。

**4. 事業者との関係を書かない**

**何社から選んだか、どういう基準で選んだか、契約後にどう管理したか。**ベンダーマネジメントは求人票に出てくる言葉です。

**5. 止まったときの話を書かない**

障害対応や、稼働後に動かなかったときの対応は、**この経歴でいちばん読まれる材料**です。書いていない方が多いのですが、うまくいった話より差が付きます。

自分の経歴がどう言い換えられるかは、一度話しながら整理したほうが早いことが多いです。[どの経験に値が付くのかから相談できます](../apply.html)。

:::insight
ここまで書いておいて逆のことを言いますが、**情報政策課にいるうちに動かないほうがよい場合もあります。**とくに、**システムの更改や標準化への対応が進行中の段階**です。この種の事業は、仕様を決めるところから稼働後の安定までを通すと、書けることが大きく変わります。**途中で抜けると「関わった」としか書けません。**通せば「調達から稼働まで一貫して担当した」と書けます。民間の情報システム部門で足りていないのは、まさにこの一貫した経験を持つ人です。稼働を見届けてから動く判断には、十分な理があります。
:::

## まとめ

- 番号法第1条は、**異なる分野に属する情報を照合して同一の者に係るものかどうかを確認できるようにする**ことを目的に掲げています。この部署の中心は**つなぐこと**です
- **開発はしていません。**やっているのは、要件を決めること、選ぶこと、動かすこと、止まったときに直させることです。これは民間の**情報システム部門**そのものです
- 庁内の「システム調達」は、求人票では**「要件定義」「RFP作成」「ベンダーマネジメント」**と書かれています。**検索する言葉を変えるところから始めてください**
- 評価が高くなるのは、**事業会社の情報システム部門／自治体を顧客にするシステム会社／業務改革・オペレーション改善／情報セキュリティ・データ保護**の4方向です
- 職務経歴書では、製品名ではなく**機能と規模**を書いてください。契約金額、業務数、データ件数、関わった課の数
- **止まったときの話を書いてください。**うまくいった話より差が付きます

在職中でも、情報収集だけでも構いません。ご利用は無料です（紹介手数料は採用企業の負担です）。

## よくある質問

### 開発経験がないと、情報システムの求人は難しいですか

職種によります。**社内SEや情報システム部門の求人では、開発経験より要件定義と調達の経験が問われるものが多くあります。**「外部に開発を委託し、社内は企画と管理を持つ」という体制の企業では、情報政策課の経験がほぼそのまま使えます。一方、自社で開発している企業の求人は、開発経験が前提になります。**求人票の「開発」の位置を確認してから応募してください。**

### 資格は取ったほうがいいですか

方向によります。情報処理技術者試験の区分のうち、**プロジェクトマネージャやシステム監査、情報処理安全確保支援士**は、経歴を補強する形で効く場面があります。ただし**「取れば転職できる」という関係ではありません。**基幹システムの更改を通した経験があるなら、そちらのほうが直接読まれます。**先に方向を決めてから、必要かどうかを判断してください。**

### 標準化への対応は、民間で説明しにくくありませんか

説明の仕方で伝わります。**「国が定めた共通仕様に、既存のシステムと業務を合わせる作業」**と言い換えてください。民間でいえば、**グループ全体の共通システムに個社のシステムを寄せる作業**に近く、統合や合併のあとに起きる仕事とよく似ています。業務側の例外をどう扱ったかまで話せると、実務経験として読まれます。
